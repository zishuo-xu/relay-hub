# ADR-002：整体设计、分层实现

- 状态：Accepted
- 日期：2026-08-06

## 背景

RelayHub 已通过 Phase 1A 证明单 Agent 的最小纵向链路。原计划下一步直接建立 PostgreSQL schema，但 Task、Run、Handoff、Review、Agent Session 和事件之间的最终关系尚未完成整体评审。如果立即固定数据表，后续多 Agent 设计很可能迫使我们反复改变核心字段和语义。

另一方面，试图在编码前确定所有未来列、索引和部署细节也会造成无证据的过度设计。

## 决策

采用“整体设计、分层实现”的方法：

1. 在 PostgreSQL 实现前，先完成面向最终目标的逻辑架构基线。
2. 基线必须覆盖领域对象、所有权、状态机、命令、事件、Agent 通信、安全边界和三条核心时序。
3. 先稳定 ID、关系、状态语义、因果引用和事实来源等高迁移成本内容。
4. Provider metadata、指标、索引和扩展 payload 等低稳定性内容允许通过 migration 演进。
5. 实现仍按最小纵向切片推进，不一次性开发全部目标能力。
6. PostgreSQL schema 从领域模型推导，不能反过来驱动领域设计。

## 为什么这样做

- 让 API、Worker、Web 和未来 Handoff 复用同一套稳定概念。
- 避免早期数据库字段偶然成为长期架构约束。
- 保留通过真实运行证据调整可变细节的空间。
- 面试时能够同时解释系统全景和阶段性实现取舍。

## 结果

下一步从 Phase 1B PostgreSQL 实现前移到 Phase 0B 整体设计基线。基线评审通过后才创建生产 schema 和 migration。

这不会推翻 Phase 1A 原型；现有代码继续作为行为验证器，用来检查后续整体设计是否仍能覆盖已跑通的链路。

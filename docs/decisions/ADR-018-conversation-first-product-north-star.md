# ADR-018：以对话线程作为多 Agent 协作主入口

- 状态：Accepted
- 日期：2026-08-13

## 背景

RelayHub 已实现真实 Agent、结构化 Handoff、独立 Review、返工循环、动态顺序交接和 Worker 失联收敛。这些能力证明了可靠运行底座，但当前产品表面仍以“创建 Task、查看技术 Timeline、等待状态迁移”为中心。

重新核对 Clowder AI 的产品结构后，参考项目的核心并不是 Git 交付流程，而是让用户在同一个多线程对话空间中与多个具名 Agent 协作。Hub 管理 Agent、模型、能力与路由，Mission Hub 承担功能治理；底层任务、调用、交接和 SOP 支撑这些体验，但不替代对话主入口。

若 RelayHub 继续优先建设 commit/apply/push 或通用工作流编辑器，会优化一个支撑环节，却偏离“用户不再充当 Agent 路由器”的核心愿景。

## 决策

1. RelayHub 的主要用户入口演进为线程化多 Agent 对话。用户可以在同一线程中通过自然语言和 `@Agent` 发起协作。
2. AgentProfile、模型连接、能力、提示词、权限和路由策略继续由集中配置中心管理。
3. Task、Run、Handoff、Review、RunOutcome、Event 和 Lease 保留为执行与治理事实。它们支撑对话，但技术 Timeline 不再是最终主界面。
4. 普通消息协调不迁移责任；只有经过平台校验的结构化 Handoff、Review 或用户命令可以改变任务责任和状态。
5. Git worktree、commit、push 和合并策略属于 Agent 工具能力或开发 SOP，可以审计和约束，但不成为新的核心领域中心。
6. 在实现前先设计 `Thread`、`Message` 与现有 `Task`、`Run` 的关系。ADR-018 只确认产品北极星，不预先批准具体表结构。
7. 每个后续大特性必须通过参考门禁：说明它对应 Chat、Hub 或 Mission/Governance 哪一层，以及它如何减少用户的人工路由负担。

## 结果

### 正向结果

- 已完成的可靠执行能力获得清楚的产品承载面，而不是继续堆叠基础设施。
- 用户与多个 Agent 的协作更自然，配置、对话和治理职责分离。
- RelayHub 与参考项目保持问题和产品思想的一致，同时继续使用独立实现和领域语言。

### 代价与风险

- 需要重新审视当前 Task 是否等同于线程，或由 Thread 包含多个 Task；在决策前不能直接加表。
- Web 信息架构需要从事件时间线优先调整为消息优先，并保持技术审计可访问。
- `@mention` 只是交互语法，必须转换为受权限、幂等和执行身份保护的平台命令，不能直接以文本驱动状态迁移。

## 被拒绝的方向

- **以 Git 交付中心作为下一条产品主线**：Git 是重要工具和证据来源，但不是多 Agent 协作平台的首要差异化能力。
- **用固定工作流编辑器替代 Agent 协作**：会把动态团队协作收缩为定制流水线，并引入不必要的 DSL 和状态复杂度。
- **只美化现有 Timeline**：视觉调整不能解决缺少多 Agent 对话、消息路由和用户自然介入入口的问题。

## 后续动作

下一项架构工作是给出 Thread/Message/Task/Run 的候选模型、状态与迁移路径，并用一个最小浏览器闭环验证：用户在同一线程 `@` 两个独立 Agent，响应、Handoff 和审计记录都能恢复且不混淆。

# ADR-025：消息路由优先的 Agent 责任接力

- 状态：Accepted
- 日期：2026-08-15

## 背景

真实浏览器验收暴露出 ADR-024 的主路径不自然：负责人提出计划、用户批准、子 Thread 执行、再等待子任务回报。一个已完成分析的子 Agent 把“等待负责人决定”表达成 `wait_for_user` 后，平台会把它理解成“等待用户”，从而让父任务卡在 `waiting_on_children`。

问题不只是终态映射。参考项目的核心协作结构不是父子任务树，而是一个 Thread 内的显式责任路由：当前 Agent 完成自己的回合后，必须把工作交给下一位 Agent、交回负责人，或明确请求用户决策。平台持久化消息、路由和执行事实，并用统一队列可靠唤醒目标 Agent。

## 决策

RelayHub 采用以下主结构，作为日常多 Agent 协作的默认路径：

```text
用户 -> 初始负责人
初始负责人 --明确交接--> 专业 Agent
专业 Agent --结果 + 明确交接--> 下一个 Agent 或负责人
负责人 --汇总--> 用户
```

1. **Thread 是协作真相，Task/Run 是执行审计。** 用户和 Agent 的可见交流始终留在同一主 Thread；Task/Run 记录一次工作和隔离执行，不替代团队对话。
2. **每次非终止回合都必须有明确去向。** 当前 Owner 只能：交给一个平台 Agent、交回负责人、请求独立 Review，或明确向用户提问。不能把“等另一个 Agent 的结论”写成 `wait_for_user`。
3. **负责人不是固定角色，而是当前持有整体目标的 Agent。** 它按任务实际需要选择产品、架构、开发、UX、测试等协作者；平台不硬编码阶段流水线。
4. **同一执行队列承接所有路由。** 用户消息、Agent 间接力、Review 和恢复都使用同一套持久事实、Outbox、队列和 Run 状态机；Agent 不轮询，也不能伪造完成。
5. **独立子 Thread 降级为例外能力。** 仅当工作长期、边界清晰、需要独立上下文或并行执行时，负责人提出可审批的“fork-and-return”计划。子 Thread 必须带回父 Thread 的路由凭据；它的终态是回报负责人，不是静默等待用户。
6. **用户是最终决策者，不是默认中转站。** 只有真正缺少业务决策、授权或外部输入时才路由给用户；常规 Agent 协作必须自动交给下一个明确责任人。

## 实施顺序

1. 修正隔离子任务的终态：它不能以 `wait_for_user` 阻塞父负责人，完成结果必须回报并恢复负责人。
2. 将 Agent Prompt 和 Web 主入口改成“选择一个负责人 -> 同 Thread 明确接力”，把 Delegation 从默认动作移为“新开独立工作”的高级动作。
3. 在持久模型中增加可投影的 `route` 事实：来源 Agent、目标 Agent、原因、回报目标和终态；所有 Run 仍由同一 Outbox/Worker 执行。
4. 最后才重做页面：主 Thread 展示责任接力线，独立 Thread 仅在用户展开时展示。

## 不做

- 不复制参考项目源码、品牌或其完整治理实现；RelayHub 只采用经验证的协作结构，并用自己的 TypeScript、PostgreSQL、BullMQ 和 Agent Adapter 实现。
- 不把产品、架构、开发、测试固化成不可变流程。
- 不删除已有隔离 Delegation 数据；旧记录继续可审计，新规则只作用于后续执行。

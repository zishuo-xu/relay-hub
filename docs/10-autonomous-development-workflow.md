# 10. 自主设计与交付工作流

- 状态：Accepted
- 日期：2026-08-12
- 取代：2026-08-11 的“单 Architect 向单 Implementer 委派”工作模式

## 1. 结论

RelayHub 改为由 Codex 直接承担总体设计、功能设计、系统设计、实现、验证、文档、提交和推送。用户只需要决定产品方向、回答真正影响结果的选择并验收可见成果，不再负责复制提示词、转交任务或协调第二名开发者。

这次调整的原因不是降低质量门槛，而是减少角色切换、重复读仓库、状态交接和文档仪式带来的等待。设计与实现由同一上下文连续完成，独立验证仍作为交付门槛保留。

## 2. 单一责任人

Codex 负责：

- 从整体目标判断下一项最有价值的纵向切片。
- 维护产品边界、领域模型、状态机、安全不变量和简洁架构。
- 自主完成前后端实现与必要的小型重构。
- 运行单元、集成、构建、浏览器和真实 CLI 验证。
- 把稳定结论和实现事实同步到已有文档。
- 创建 focused commit，推送 `origin/main`，确认远端一致与工作区干净。

用户负责：

- 决定会改变产品方向、成本、安全边界或使用体验的重要取舍。
- 提供只有用户掌握的凭证、外部权限或业务事实。
- 对阶段性可见结果提出偏好和反馈。

## 3. 每个切片的工作闭环

```text
整体目标与当前事实
-> 选择一个最小但可见的纵向切片
-> 明确价值、范围、不变量和验收标准
-> 直接实现
-> 自动化、集成、浏览器或真实运行验证
-> 修复 Findings 并复验
-> 更新文档
-> commit + push + clean worktree
```

规则：

1. 同一时刻只推进一个主要实现切片，避免半成品并行堆积。
2. 优先复用 Task、Run、Handoff、Review、Outbox 和现有 Adapter 边界，不为单一需求引入通用 Workflow Engine。
3. 大型、高风险或跨会话工作可以创建 Work Item，作为冻结范围和证据载体；小型修复无需创建 Work Item。
4. 代码写完不等于完成。至少需要与风险相称的测试，涉及用户路径时补浏览器验收，涉及真实 Agent 时尽可能补真实 CLI 冒烟。
5. 测试必须使用隔离数据库或临时仓库，不删除正式 PostgreSQL、Redis、Task、Run、Handoff、Worktree 或用户数据。
6. 每次代码或文档改动都要提交并推送 GitHub，不把已完成改动只留在本地。

## 4. 设计与 UX 原则

- 架构保持模块化单体：模型负责推理，Agent CLI 负责工具执行，RelayHub 负责身份、编排、权限、审计和协作协议。
- Orchestrator 是 Task/Run/Handoff/Review 状态迁移的唯一写入者；模型只提出结构化意图。
- 平台级 Agent 与 CLI 内部子 Agent 必须保持身份和权限隔离。
- 页面优先在一个视口内表达当前任务、当前责任人、运行状态和 Timeline；长列表使用区域内滚动，低频配置按需展开。
- 使用克制的状态色、清楚的层级和留白，保持 RelayHub 独立的组件与视觉语言。

## 5. Work Item 的新定位

`docs/work-items/` 保留为重大特性的历史设计与验收记录，不再是每次开发的强制任务队列，也没有用户中转提示词或 Implementer 状态交接。

已有 `WI-P3.4-001` 保留完整历史：它记录了委派实现、架构复验、问题修复、浏览器验收和真实双 Agent 运行证据。后续大型切片若使用 Work Item，可简化为：`PLANNED -> IN_PROGRESS -> VERIFYING -> DONE/BLOCKED`，所有状态均由 Codex维护。

# 08. 讨论沉淀规则

## 目的

RelayHub 同时是实现项目和面试学习材料。讨论中出现的高价值结论如果只留在聊天里，后续容易丢失，也容易让代码、架构文档和面试表述互相矛盾。

因此采用以下默认规则：

> 当一轮讨论形成稳定的项目结论时，在同一轮将其提炼并写入最相关文档，不需要用户再次提醒。

## 哪些内容自动保存

- 项目范围和产品边界。
- 架构决策及其原因。
- 数据所有权、通信协议和安全边界。
- 已接受或明确拒绝的技术方案。
- 路线顺序、阶段目标和验收标准变化。
- 经过测试、构建或运行验证的实现事实。
- 能准确对应当前实现的面试表达。

## 哪些内容不直接保存为结论

- 随口提出但尚未讨论的设想。
- 未验证的性能、规模或安全结论。
- 临时调试输出和一次性命令日志。
- 模型隐藏推理过程。
- 与 RelayHub 无关的内容。

有保留价值但尚未确定的想法，可以记录为 `Proposed` 或 `Open question`，不能写成已经决定或实现。

## 状态标签

| 标签 | 含义 |
|---|---|
| `Accepted` | 当前已经达成一致的设计方向 |
| `Proposed` | 值得考虑，但还没有决定或实施 |
| `Open question` | 需要更多证据或用户选择 |
| `Implemented` | 已由当前代码和验证证据确认 |

## 边界

自动更新文档不等于自动扩展实现范围。如果讨论带来新的数据库、外部服务、权限、安全或大规模代码变更，应先记录结论，再根据用户授权进入实现。
